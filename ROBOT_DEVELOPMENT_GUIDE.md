# Game of Prompts — Solver Development Guide

## 1. Introduction

Game of Prompts (GoP) is a decentralized competitive execution protocol in which participants develop autonomous Solvers capable of interacting with deterministic Game-Services under verifiable execution constraints.

Unlike conventional online competitions, GoP does not rely on centralized execution servers. Each participant independently executes the competition environment locally and submits cryptographic evidence of execution to the blockchain.

The protocol is therefore based on three principles:

1. Deterministic execution
2. Cryptographic verifiability
3. Decentralized computation

## 2. Fundamental Architecture

A competition in Game of Prompts consists of two isolated executable systems:

| Component      | Description                                                                           |
| -------------- | ------------------------------------------------------------------------------------- |
| Game-Service   | Virtualized execution environment defining the rules and mechanics of the competition |
| Solver-Service | Virtualized autonomous agent developed by the participant                             |

Both are distributed and executed as independent virtualized services, each with its own operating system, filesystem, runtime environment, and execution constraints.

The Game-Service acts as the authoritative environment. The Solver-Service interacts with it through predefined interfaces specified by the competition.

## 3. The Solver Model

A Solver is an autonomous decision system.

Its function is to receive a state generated by the Game-Service and produce a valid action according to the competition rules.

Abstract formulation:

```text id="0x7cx1"
Input State → Decision Logic → Output Action
```

Examples:

| Input             | Logic                    | Output     |
| ----------------- | ------------------------ | ---------- |
| Board state       | Pathfinding algorithm    | `"UP"`     |
| Poker state       | Probabilistic evaluation | `"FOLD"`   |
| Constraint system | Search procedure         | `"X = 10"` |

The internal implementation is unrestricted provided that execution remains deterministic and compliant with the competition constraints.

## 4. Competition Lifecycle

The complete lifecycle of participation is summarized below.

```text id="41x95m"
1. Develop Solver
        ↓
2. Package Solver-Service
        ↓
3. Download Competition Game-Service
        ↓
4. Submit Solver ID On-Chain During Seed Phase
        ↓
5. Wait Until Seed Finalization
        ↓
6. Execute Game-Service Locally With Solver
        ↓
7. Generate Commitment
        ↓
8. Submit Participation On-Chain
        ↓
9. Validation And Ranking
        ↓
10. Reward Distribution
```

## 7. Acquiring a Game-Service

Each competition provides its own Game-Service package.

Participants must download the package corresponding to the target competition.

Example:

```bash id="b7q9j4"
nodo download {GAME_SERVICE_URL}
```

The Game-Service defines:

* execution rules,
* communication interfaces,
* scoring logic,
* deterministic constraints,
* validation procedures.

```python id="0tm2ak"
app = Flask(__name__)

@app.post("/solve")

    return "UP"

app.run(host="0.0.0.0", port=8080)
```

The exact interface specification depends entirely on the competition Game-Service.

## 9. Local Simulation

Before participating in a live competition, the full execution flow should be validated locally.

Recommended procedure:

1. Launch the Game-Service locally
2. Connect the Solver-Service
3. Execute repeated simulations
4. Validate:

   * correctness,
   * determinism,
   * latency,
   * fault handling,
   * edge-case behavior.

The production environment reproduces this same execution model.

## 11. Seed Phase

The Seed phase establishes the deterministic parameters of the competition.

During this phase:

* participants may submit Solver IDs on-chain,
* the Seed remains mutable,
* any participant may modify the Seed through valid blockchain interactions.

However, the Seed becomes fixed several blocks before the competition deadline, guaranteeing a deterministic final state prior to execution.

Importantly, participants do not modify an already submitted Solver. Instead, they may upload and register a new Solver package while the Seed phase remains open.

## 12. On-Chain Registration

During the Seed phase, participants publish the hash of their `.celaut.bee` package on-chain.

This establishes only one property:

* timestamped existence.

The blockchain therefore proves that a specific Solver package existed before the final Seed became known.

## 13. Execution Phase

After Seed finalization:

1. The participant launches the Game-Service locally
2. The Solver-Service package is provided to the Game-Service
3. Deterministic execution begins
4. The Game-Service generates a Commitment
5. The participant submits an on-chain participation transaction containing the Commitment

All execution occurs locally on participant-controlled infrastructure.

No centralized authority executes matches on behalf of users.

## 14. Execution Constraints

### Deterministic Sandbox

Execution occurs inside isolated virtualized environments.

Restrictions may include:

* no internet access,
* restricted filesystem visibility,
* isolated runtimes,
* deterministic resource limits.

### Performance Constraints

Execution latency is competition-critical.

A Solver-Service that exceeds timing constraints may fail to produce a valid participation.

Efficiency is therefore a primary engineering concern.

### Tie Resolution

If multiple participants achieve valid results, ranking is determined according to the scoring rules and on-chain ordering constraints defined by the competition.

### Algorithmic Freedom

Participants may employ any deterministic computational methodology, including:

* classical algorithms,
* heuristic systems,
* reinforcement learning,
* symbolic reasoning,
* local language models,
* hybrid architectures.

Complexity alone does not confer advantage. Reliability under constrained execution is the determining factor.

## 15. Rewards and Competitive Outcome

For each competition, rewards consist of:

1. The accumulated fee pool, minus:

   * creator commissions,
   * judge commissions,
   * protocol commissions.

2. The competition NFT associated with the game.

Rewards are assigned to the participant achieving the highest validated score.

## 16. Engineering Considerations

A competitive Solver-Service must satisfy four properties:

1. Determinism
2. Reliability
3. Computational efficiency
4. Robustness under adversarial or unexpected states

The principal challenge is not merely producing intelligent behavior, but maintaining valid execution across every reachable state of the Game-Service.

In Game of Prompts, competitive advantage emerges from correctness under constrained decentralized execution.
